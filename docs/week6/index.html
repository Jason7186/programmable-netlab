What I learned

Describe your design: hypervisors, tenants, VNIs and addresses. Which tenants overlap, and why did you place each VM where you did?

My underlay is 10.85.0.0/24 with three hypervisors: hv1 (10.85.0.1), hv2 (10.85.0.2) and hv3 (10.85.0.3). There are two tenants, red (VNI 100) and blue (VNI 200), and both use 10.85.50.0/24, so their addresses overlap on purpose. Red has red1 (.10) on hv1, red2 (.11) on hv2 and red3 (.12) on hv3, so it spans all three hypervisors and I can watch flooding reach more than one VTEP. Blue has blue1 (.10) on hv1 and blue2 (.11) on hv3, so its traffic also crosses the overlay. hv1 and hv3 host both tenants, so VMs with the same IP sit on the same hypervisor and must be kept apart. hv2 only hosts red, so it has no VTEP for VNI 200.

Two of your VMs have the same IP address. Using your evidence, explain how a ping reaches the right one â€” and what would have to go wrong for one tenant to see another's traffic.

red2 and blue2 both have 10.85.50.11. When red1 pinged it, red1 learned MAC 02:00:00:64:00:0b, which is red2 (0x64 = VNI 100), and the capture on blue2 saw 0 packets. When blue1 pinged the same address, it learned 02:00:00:c8:00:0b, which is blue2 (0xc8 = VNI 200), and the hv3 underlay capture shows that traffic carried as vni 200. Each tenant has its own bridge and VXLAN device on every hypervisor, so red’s frames only enter br100, only leave with VNI 100, and are only delivered into red’s bridge at the other end. For one tenant to see another’s traffic, this mapping would have to break. For example, two tenants could be given the same VNI, a VM port could be put in the wrong bridge, or someone on the underlay could forge VXLAN packets with another tenant’s VNI, since VXLAN has no authentication.

Using your evidence, explain what was flooded, to which hypervisors, and what each VTEP learned. With 50 hypervisors in one VNI, how many copies would one broadcast need â€” and how would EVPN change that?

Before any traffic, hv1’s vxlan100 table only had two flood entries, to 10.85.0.2 and 10.85.0.3. When red1 pinged red2, its ARP request was a broadcast, so hv1 sent one copy to each of hv2 and hv3 (head-end replication). The capture on hv3 shows exactly one packet: that ARP request in vni 100 from 10.85.0.1. None of the pings appear, because they only went between hv1 and hv2. Afterwards hv1 had learned red2’s MAC behind 10.85.0.2, and hv3 had learned red1’s MAC behind 10.85.0.1 from the flooded ARP alone. With 50 hypervisors in one VNI, one broadcast would need 49 copies from the sender. EVPN uses BGP to tell every VTEP in advance which MAC is behind which VTEP, so unknown traffic no longer has to be flooded to learn, and ARP can be answered locally (ARP suppression).

Compare your two MTU fixes using your measurements. Which would you choose for a data centre, what does each cost, and who has to change what?

With tenant MTU 1500 on a 1500 underlay, the largest ping that worked was 1422 bytes, a 1450-byte packet, because 1450 + 50 = 1500. Larger pings were lost with no error, and iperf3 moved 0 bytes: a black hole. With fix A (tenant MTU 1450), 1422 worked, 1423 failed immediately with a local “message too long, mtu=1450”, and iperf3 reached 4.87 Gbit/s. With fix B (underlay MTU 9000), tenants kept 1500: 1472 worked, 1473 failed locally at mtu=1500, and iperf3 reached 5.31 Gbit/s, about 9% faster because each segment carries more data. I would choose fix B, because tenants change nothing and get a normal 1500 MTU. Its cost falls on the network team, who must enable jumbo frames on every hypervisor NIC and underlay switch, and one missed link brings the black hole back. Fix A puts the cost on tenants instead: every VM must be set to 1450, and each packet carries 50 bytes less data.

If your hypervisors' VTEPs were P4 switches running the lecture's vtep.p4, what would have to fill the vtep_encap table, and how? What would replace flood-and-learn?

A P4 VTEP does not learn by itself, so the control plane must fill vtep_encap. Each entry maps a VNI and destination MAC to the remote VTEP’s underlay IP for the outer header. For example, VNI 100 and 02:00:00:64:00:0b map to 10.85.0.2. A controller could write these entries through P4Runtime, working them out from my overlay.yaml, because the design already says which VM, MAC and hypervisor belong together. In a real data centre they would come from the orchestrator or from EVPN BGP routes. This replaces flood-and-learn: every VTEP knows where each MAC is before the first packet, and only true broadcasts still need a list of VTEPs to copy to.
